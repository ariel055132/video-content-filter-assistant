## 核心重點

1. **長任務會放大方向錯誤。** TED 從模型長時間工作的親身體驗，轉向討論如何讓 Agent 收斂；他主張以可用改動、人工審查負擔與成本衡量成果，而非只看執行時間。
2. **Goal、Spec、Plan 分工不同。** Goal 說明要解決的問題與期望結果；Spec 定義功能邊界、完成條件與驗證；Plan 是實作路線，可在假設改變時重擬。他將文件比作新的原始碼，意在強調需求品質的重要性。
3. **上下文要能跨對話延續。** 他使用「大腦 repo」連接工作資訊、會議紀錄與各專案；每次 session 回寫摘要、進度與決策。專案另保留架構、命名、不可修改的範圍、品質要求及任務清單。
4. **Harness 是完整工作環境與驗收流程。** 它涵蓋 Agent 能看見與操作什麼、如何保存狀態、如何判定完成、失敗怎樣復原，以及人負責哪一層。測試、build、lint、型別檢查、整合與 UI 檢查應按任務分層，多 Agent 不應無條件全開。
5. **交付還要通過「理解關卡」。** 測試成功之外，人應能解釋改了什麼、目的、失敗與回滾方式、是否過度設計。他用不同層級架構圖輔助討論；最後延伸至職涯與生活選擇，提醒 AI 省下的能力也可以用來探索自己想做的事。

## 實際解讀

**助理建議，並非使用者已承諾的行動：** 在下一個可回復的小型開發任務試用以下任務卡，記錄是否減少重工與審查時間。

| 欄位 | 要寫清楚的內容 |
|---|---|
| Goal | 要改善哪個使用者問題，何種結果才有價值。 |
| Spec | 做與不做的範圍、不可破壞的條件、可檢查的完成證據。 |
| Plan | 當前路線與假設；遇到什麼結果應停下來重擬。 |
| 狀態交接 | 已完成、待完成、決策理由、阻礙；附能核對的檔案或測試結果。 |
| 驗證 | 依變更影響挑選檢查；先確定驗收條件，再決定是否需要更多 Agent。 |
| 理解關卡 | 關掉 AI 的解釋，自己說出改了什麼、資料如何流動、怎麼失敗與回滾；答不出來的部分再追查。 |

不要把「文件變多」當成改善指標。用可用成果、返工、審查耗時和自己能否解釋關鍵決策，觀察這個流程有沒有幫助。
